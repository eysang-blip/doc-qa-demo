# PUBG 패치노트 문서 Q&A와 신뢰성 검증

PUBG 패치노트 요약 문서 5개를 근거로 질문에 답하고 패치를 요약하는 LLM 데모입니다.
**만드는 것보다 검증에 초점을 맞췄습니다.** 26개 평가 질문으로 답변을 자동 채점해 SQLite에 기록했습니다.
그리고 프롬프트를 바꿀 때마다 무엇이 좋아지고 무엇이 나빠지는지 비교했습니다.

> **입력 문서에 대해:** `docs/patch_summary.txt`는 공식 패치노트 원문이 아니라, AI로 작성한 **요약본**입니다(업데이트 42.2 ~ 44.1).
> 저작권과 정확성 문제로 저장소에는 포함하지 않았습니다.
>
> **AI 활용에 대해:** 코드는 AI 코딩 도구(Claude Code)의 도움을 받아 작성했습니다.
> 실행 결과 확인, 오류 원인 분석, 평가 설계와 결과 해석은 직접 했습니다.

## 기능

| 기능 | 설명 |
|---|---|
| 문서 분할 | 정규식으로 `1. 업데이트 44.1 (2026.11.03)` 형식의 제목을 찾아 패치 단위로 나눔 |
| 질의응답 | 문서 내용만 근거로 답하고 `(출처: 패치 44.1)` 형식으로 근거 패치 표시. 문서에 없으면 "문서에 해당 내용이 없습니다." |
| 3줄 요약 | `/요약 44.1` 입력 시 해당 패치를 3줄로 요약 |
| 자동 평가 | 26개 질문 실행, 규칙 기반 채점, 결과를 SQLite에 저장 |
| 결과 분석 | 실행별·유형별 정답률, 오답 목록, 두 실행 간 문항별 비교(SQL) |

## 구조

```
doc-qa-demo/
├─ main.py               # 문서 로드·분할, Gemini 호출, 질의응답·요약, 대화형 실행
├─ eval.py               # 평가 실행, 채점, SQLite 기록, 리포트·비교·재채점
├─ eval_questions.json   # 평가 질문 26개와 정답 기준
├─ docs/patch_summary.txt  (저장소 미포함)
├─ qa_log.db               (저장소 미포함, 평가 실행 시 생성)
└─ .env                    (저장소 미포함, API 키)
```

- **모델:** Google Gemini `gemini-3.5-flash-lite`, temperature 0
- **사용 기술:** Python 3.14, `google-genai`, `python-dotenv`, SQLite(`sqlite3` 표준 라이브러리)

## 실행 방법

```bash
pip install google-genai python-dotenv
```

`.env` 파일에 API 키를 넣습니다. 키는 [Google AI Studio](https://aistudio.google.com/apikey)에서 받을 수 있습니다.
```
GEMINI_API_KEY=발급받은_키
```

`docs/patch_summary.txt`에 아래 형식으로 문서를 넣습니다.
```
1. 업데이트 44.1 (2026.11.03)
(본문)
2. 업데이트 43.2 (2026.10.13)
(본문)
```

```bash
python main.py                        # 대화형 질의응답 (/요약 44.1 = 3줄 요약)
python eval.py --prompt v3            # 평가 실행 후 리포트 출력
python eval.py --report               # 저장된 결과만 집계
python eval.py --compare 3 5          # run 3과 run 5를 문항별로 비교
python eval.py --regrade 3            # 저장된 답변을 현재 채점 규칙으로 다시 채점 (API 호출 없음)
```

## 평가 방법

**질문 26개** ([eval_questions.json](eval_questions.json))

| 유형 | 문항 수 | 확인하는 것 |
|---|---|---|
| 단일사실 | 15 | 한 패치 안의 수치·이름을 정확히 찾는지 |
| 문서없음 | 5 | 문서에 없는 내용을 지어내지 않고 거절하는지 |
| 잘못된 전제 | 2 | 질문 속 패치 번호가 틀렸을 때 바로잡는지 (예: "43.2에서 추가된 RPD") |
| 다중패치 | 2 | 여러 패치에 걸친 변경을 모두 찾는지 |
| 계산 | 1 | 변경 전후 값의 차이를 답하는지 |
| 부분정보 | 1 | 일부만 문서에 있을 때 있는 부분을 답하는지 |

**채점 (규칙 기반, 자동)**
- 답이 있는 질문은 정답 키워드가 모두 들어 있고, 기대한 출처 패치를 모두 인용해야 정답입니다.
- 답이 없는 질문은 답변이 "문서에 해당 내용이 없습니다"로 시작해야 정답입니다.
- 오답에는 실패 이유를 자동으로 분류해 붙입니다. 환각, 과잉 거절, 키워드 누락, 출처 누락, API 오류로 나눕니다.

**SQLite 스키마**
- `runs`: 평가 1회 (실행 시각, 모델, 프롬프트 버전, 메모)
- `results`: 질문 1개의 결과 (질문, 기대 답, 실제 답변, 정답 여부, 실패 이유, 응답 시간), `run_id`로 `runs`와 연결

`--compare`는 `results` 테이블을 셀프 조인합니다. 같은 질문에서 두 실행의 결과가 달라진 문항만 뽑아 개선과 악화로 나눕니다.

## 결과 (2026-11-11, 26문항, 같은 모델)

| 유형 | v1 | v2 | v3 |
|---|---|---|---|
| 단일사실 (15) | 15 | 15 | 15 |
| 문서없음 (5) | **5** | **2** | **5** |
| 잘못된 전제 (2) | 0 | 2\* | 0 |
| 다중패치 (2) | 2 | 1 | 2 |
| 계산 (1) | 0 | 0 | 1 |
| 부분정보 (1) | 1 | 1 | 0 |
| **합계** | **23 (88.5%)** | **21 (80.8%)** | **23 (88.5%)** |

\* v2의 프롬프트 예시 문장이 평가 문항 Q20의 정답과 같았습니다. 그래서 이 점수는 실제 성능으로 보기 어렵습니다(아래 참고).

### 프롬프트 개선 과정

**v1 (기본):** 문서 근거로만 답하고, 없으면 거절하도록 했습니다.
→ 지어낸 답은 0건이었습니다. 하지만 "43.2에서 추가된 RPD의 피해량은?"처럼 패치 번호가 틀린 질문은 통째로 거절했습니다(실제로는 42.3에서 추가).

**v2 (전제 정정 규칙 추가):** "전제가 틀리면 바로잡고 답하라"는 규칙과 예시 문장을 넣었습니다.
→ 잘못된 전제 문항은 맞혔지만, **지어낸 답이 0건에서 3건으로 늘었습니다.**
- "43.2에서 새로 추가된 총기는?"(정답: 없음)에 예시 문장을 그대로 따라 RPD를 답했습니다.
- "42.2 경쟁전 시즌 보상은?"(정답: 없음)에 44.1의 보상을 대신 답했습니다.
- 예시 문장이 평가 문항 정답과 같았습니다. **평가 데이터가 프롬프트에 새 나가 점수가 부풀려졌다는 것**을 확인했습니다.

**v3 (실패 분석 반영):** 구체적 예시를 빼고, 전제 정정은 "무기·기능 이름을 댔는데 패치 번호만 틀린 경우"로 좁혔습니다. 무기군(LMG) 단위 변경을 개별 무기 질문에 포함하는 규칙과 증감 계산 규칙도 추가했습니다.
→ 지어낸 답은 다시 0건이 됐고 계산 문항도 개선됐습니다. 그러나 전제 정정은 여전히 실패했고, 부분정보 문항(44.2 예정 사항)은 새로 거절했습니다.

**결론:** 이 모델에서는 "모르면 거절"과 "틀린 전제를 바로잡기"가 서로 부딪쳤습니다.
문서 기반 Q&A에서는 지어낸 답이 더 큰 문제라고 판단해 **v3를 기본값으로 정했습니다.**

### 평가 과정에서 고친 문제

| 문제 | 원인 | 수정 |
|---|---|---|
| 모델 호출 404 | `gemini-2.5-flash`가 신규 사용자에게 막힘 | 사용 가능한 모델 목록을 조회해 교체 |
| 응답 없이 멈춤 | 특정 모델(`3.8-flash`)이 응답하지 않음 | 60초 타임아웃 추가, 모델 교체 |
| 첫 평가 중 429 오류 | `3.5-flash` 무료 한도가 하루 20회 | 한도가 넉넉한 `flash-lite`로 교체, 요청 간 4초 대기, 503·429 재시도 |
| 채점 오판 (정답 처리) | 숫자 키워드 `4`가 `43.2` 안에서도 일치 | 숫자 앞뒤 경계 검사 |
| 채점 오판 (오답 처리) | `2026년 11월 3일`을 `2026.11.03`과 다르게 판단 | 같은 뜻의 다른 표현 허용(`a\|b`), 저장된 답변 재채점 기능 추가 |

## 한계

- 평가 문항이 26개뿐이라 버전 간 차이 1~2문항은 우연일 수 있습니다.
- 채점은 키워드 규칙 기반이라 표현이 다르면 오판할 수 있습니다. 오답은 실제 답변을 직접 확인했습니다.
- 문서가 5개로 짧아 질문마다 전체 문서를 프롬프트에 넣었습니다. 검색 단계가 없으므로 RAG가 아니라 "문서 기반 Q&A"로 부릅니다.
- 같은 질문 세트로 프롬프트를 고쳤기 때문에 이 질문들에 과적합됐을 수 있습니다.
- 입력 문서가 요약본이라, 답이 정확해도 공식 패치노트와는 다를 수 있습니다.
